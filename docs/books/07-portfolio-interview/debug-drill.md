# Самостоятельные debug-drill

Три сценария самодиагностики на учебных fixture из `labs/`. Цель — не «знать ответ», а пройти путь
симптом → гипотезы → проверка → исправление → доказательство, что починил. Клиентские данные, ключи
и платные вызовы модели не нужны: drill 1 и 2 полностью локальные, drill 3 делает один бесплатный запрос
к каталогу моделей провайдера.

## Правила

- Читай раздел «Решение» только после того, как записал свою гипотезу и результат проверки.
- Засекай фактическое время каждого drill и записывай его в `career/mock-1.md` рядом со слабыми темами;
  плановые оценки ниже — ориентир до хронометража, не норматив.
- `ERROR`, «не воспроизвелось» и «не понял» — допустимые записи. Не засчитывай drill, если сработал
  обход (например, запрос под административной ролью): это ложное исправление, и оно отмечается отдельно.
- Один решённый drill — обязательный минимум дня 7. Остальные два — расширение.

## Drill 1. Все запросы возвращают 0 строк, хотя данные загружены

**День и лаба:** день 3, `labs/day3-pgvector` (см. [главу 2 дня 3](../03-vector-stores-and-ingestion/chapter-02.md)).
**Нужно:** контейнер `pg` из `docker-compose.yml`, применённый `schema.sql`, переменные `PG_APP_PASSWORD` и `PG_DSN`.
Снимок дня 2 не обязателен: строки создаются синтетическими векторами. План: 20–30 минут.

### Симптом

Коллега прислал команду и вывод: «tenant задан, а `count` равен нулю; под `rag_admin` строки видны — значит,
RLS сломан, давай выдадим приложению админскую роль».

Воспроизведение. Сначала две учебные строки (администратором, только для drill):

```bash
cd ~/proj/ai-labs/day3-pgvector
docker compose exec -T pg psql -U rag_admin -d rag -v ON_ERROR_STOP=1 -c "INSERT INTO chunks (id, tenant_id, filename, chunk_index, text, embedding) VALUES ('drill:1', 1, 'drill.md', 0, 'учебная строка tenant 1', array_fill(0.1::real, ARRAY[1536])::vector), ('drill:2', 2, 'drill.md', 1, 'учебная строка tenant 2', array_fill(0.2::real, ARRAY[1536])::vector) ON CONFLICT (id) DO NOTHING;"
```

Теперь команда коллеги от прикладной роли:

```bash
docker compose exec -T -e PGPASSWORD="$PG_APP_PASSWORD" pg psql -h 127.0.0.1 -U rag_app -d rag -c "SELECT set_config('app.tenant_id', '1', true)" -c "SELECT count(*) FROM chunks"
```

Ожидаемый вывод второй команды — `0`, хотя строка tenant 1 существует.

### Что проверить до чтения решения

1. Что возвращает `SELECT current_setting('app.tenant_id', true)` третьей командой `-c` в том же вызове `psql`?
2. Чем отличаются `set_config(name, value, true)` и `SET name = value` по времени жизни значения? Прочитай
   описание третьего аргумента `set_config` в документации PostgreSQL.
3. Как `psql` выполняет несколько `-c`: в одной транзакции или в отдельных?
4. Почему вариант «запустить под `rag_admin`» показывает строки и почему это не исправление? Сравни с
   политикой в `schema.sql` и проверкой роли в начале `rls_demo.sql`.
5. Как тот же tenant устанавливает `PgStore._rows` в `pgstore.py`, и в чём отличие от команды коллеги?

Запиши гипотезу одной фразой и команду, которой её проверил.

### Решение

`set_config(..., true)` действует только до конца текущей транзакции. В `psql` без флага `-1` каждая команда
`-c` выполняется в собственной транзакции, поэтому значение исчезает сразу после первой команды, политика
получает пустую строку, `NULLIF` превращает её в `NULL`, и таблица становится пустой для этой сессии. RLS
работает правильно: нет tenant — нет строк.

Административная роль обходит политику потому, что `FORCE ROW LEVEL SECURITY` не действует на суперпользователя
и роли с `BYPASSRLS`. Выдать приложению такую роль — отключить изоляцию, а не починить запрос.

Исправление — задавать tenant в той же транзакции, что и запрос. Для `psql` это либо сессионный `SET`, либо
явная транзакция:

```bash
docker compose exec -T -e PGPASSWORD="$PG_APP_PASSWORD" pg psql -h 127.0.0.1 -U rag_app -d rag -c "SET app.tenant_id = '1'; SELECT tenant_id, count(*) FROM chunks GROUP BY tenant_id;"
docker compose exec -T -e PGPASSWORD="$PG_APP_PASSWORD" pg psql -h 127.0.0.1 -U rag_app -d rag -c "BEGIN; SELECT set_config('app.tenant_id', '2', true); SELECT tenant_id, count(*) FROM chunks GROUP BY tenant_id; COMMIT;"
```

В коде именно так устроен `PgStore._rows`: `set_config` внутри `conn.transaction()` перед каждым запросом.

### Как убедиться, что починил

- Первая команда показывает только `tenant_id = 1`, вторая — только `tenant_id = 2`.
- Без tenant результат по-прежнему пустой: `-c "SELECT count(*) FROM chunks"` даёт `0`.
- `rls_demo.sql` от `rag_app` проходит все проверки (команда запуска — в главе 2 дня 3).
- Учебные строки удалены администратором: `DELETE FROM chunks WHERE filename = 'drill.md';`.

Слабая тема, если споткнулся: область действия GUC и транзакций в PostgreSQL, отличие сессии от транзакции в psycopg3.

### Решение

Размерность — часть типа колонки: `vector(1536)` принимает только векторы длины 1536, и это правильное
ограничение, а не помеха. Векторы разных моделей несравнимы даже при одинаковой размерности: расстояние между
эмбеддингом запроса от одной модели и документа от другой не имеет смысла. Поэтому смена модели — это отдельная
колонка или таблица с собственной размерностью и собственным индексом, полная переиндексация, двойная запись
на время миграции и переключение чтения после проверки на golden-наборе.

Предложение убрать размерность — ложное исправление: колонка без размерности примет что угодно, но HNSW-индекс
на ней не построить без фиксированной длины, а поиск станет смешивать несовместимые пространства и молча
выдавать мусор. Отказ `load.ipynb` с понятным сообщением — защита от именно этого сценария; тот же класс ошибки в
web-agent проявлялся как `dimension mismatch` в Chroma.

Минимальное корректное расширение (расширение, не обязательный минимум): таблица `chunks_e5` с
`embedding vector(384)` и `lab_snapshot_e5`, отдельные индексы, отдельный параметр таблицы в `load.ipynb` и
`pgstore.py`, и одинаковые запросы к обеим таблицам в `eval_pg.ipynb` для сравнения качества.

### Как убедиться, что починил

- Объяснение записано без подсказок и содержит три пункта: тип фиксирует размерность, пространства моделей
  несовместимы, индекс требует фиксированной длины.
- Если реализовал расширение: `load.ipynb` загружает `chunks_e5` в отдельную таблицу, `\d chunks_e5` показывает
  `vector(384)`, `eval_pg.ipynb` даёт строки для обеих таблиц, а исходная `chunks` не изменилась.

Слабая тема, если споткнулся: типы pgvector и требования индексов, план миграции модели эмбеддингов из дня 3.

### Решение

Мягкий бюджет агента считается по прайсу: `output_allowance` вычисляет, сколько токенов ответа можно
позволить в остатке `COST_CAP`, и при `p_out <= 0` возвращает `0`. С нулевыми ценами каждый ход получает
`allowance` меньше 32, `call_llm` ставит `stop_reason = "недостаточный остаток soft-бюджета"`, и агент
останавливается до первого вызова инструмента. «Исправление нулями» превращает отказ на старте в бессмысленный
отказ на первом ходе и заодно отключает учёт расходов.

`ValueError` — прайс известен, но не позволяет ограничивать расход (бесплатная модель без цены выхода).
`StopIteration` — идентификатор отсутствует в каталоге: опечатка или снятая модель. Исправления разные:
в первом случае — выбрать модель с положительной ценой выхода (или осознанно вести отдельный режим без
бюджета, честно отметив в отчёте, что soft-бюджет выключен), во втором — взять точный идентификатор из
`/models`.

### Как убедиться, что починил

- `python -c "import asyncio, agent; print(asyncio.run(agent.pricing()))"` с рабочей моделью печатает два
  положительных числа.
- `python -c "from agent import output_allowance; print(output_allowance(0.05, 3000, 1e-6, 4e-6, 400))"`
  даёт положительное число (цены здесь условные, для проверки формулы).
- Понимаешь и можешь объяснить, почему учебный агент предпочитает остановиться, а не работать с неизвестной
  стоимостью, и чем soft-бюджет отличается от лимита у провайдера.

Слабая тема, если споткнулся: устройство бюджета агента и остановок в `agent.py`, разница между отсутствием
данных и нулевым значением в учёте.
