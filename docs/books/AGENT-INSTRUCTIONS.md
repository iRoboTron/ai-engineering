## 🚦 Главное правило

Готовность текста, offline-проверки и выполненная лабораторная — разные статусы.

```bash
python3 scripts/sync_labs.py
python3 scripts/build_question_bank.py
python3 scripts/check_project.py
npm run test:reader
```

Если браузер Playwright нужной ревизии не установлен, локально подходит системный Chrome:
`CHROME_PATH=/usr/bin/google-chrome npm run test:reader` (CI ставит chromium сам).

Команды выполняются из корня проекта. Отдельный структурный lint:
`cd docs/books && python3 validate-book.py 0N-slug`.
Без offline gate текст не публикуется. Его PASS не заменяет модельный/API прогон:
записывай что действительно проверено и что осталось внешней проверкой.

## Кто читатель

Читатель — автор серии. Он **не новичок**: программист с DevOps-фундаментом (Linux, Docker, nginx,
PostgreSQL, CI/CD, мониторинг), у которого в проде уже работают:

- `~/proj/web-agent` — multi-tenant RAG-платформа: FastAPI, ChromaDB (коллекция на tenant), PostgreSQL + Alembic,
  `RecursiveCharacterTextSplitter` (500/50), эмбеддинги `text-embedding-3-small` через OpenRouter,
  Telegram-бот, виджет, админка с RBAC, честный fallback со сбором лидов, CI/CD (Ansible rolling update, self-test-гейт).
  Прод: agent1.adelfos.ru, ksm.adelfos.ru. Код RAG: `services/agent-api/app/rag/{retriever,embeddings,chain}.py`,
  индексация: `services/doc-parser/app/indexer.py`.
- `~/proj/ai-agent-memory` — сервис памяти агентов: FastAPI + ChromaDB + `all-MiniLM-L6-v2` + PostgreSQL (LXC 115, `http://100.69.146.20:443`).
- Hermes Agent в Telegram (LXC 103): systemd, OpenRouter, прокси через socks5 при геоблоке.
- Ollama и Open-WebUI (книга 23 курса devops), ComfyUI с API на ПК с RTX 3070 Ti.
- Homelab: Proxmox `pxhome`, LXC-контейнеры, nginx на LXC 109, NPM на LXC 101.

Поэтому: **не объяснять Docker, Postgres, HTTP, Python.** Объяснять то, что относится к LLM/RAG/агентам,
и всегда связывать с тем, что у читателя уже есть («в web-agent это делается так-то, а индустрия называет это …»).

Цель читателя — **пройти собеседование на AI/LLM-инженера в РФ** и начать откликаться со дня 2.
Каждая глава отвечает на вопрос «как это поможет на собеседовании или в портфолио».

## Формат книги-дня (одинаков для книг 01–06; книга 07 — см. её ТЗ)

```
0N-slug/
├── book.md          ← цель дня, тайминг по часам, оглавление, что будет в конце дня
├── chapter-01.md    ← Суть      (конспект, 1–1.5 ч чтения, 6–10 страниц)
├── chapter-02.md    ← Лаба      (пошагово, 2–3 ч, в СВОИХ проектах)
├── chapter-03.md    ← Вопросы собеседования (15–20 вопросов с ответами, 0.5–1 ч)
├── chapter-04.md    ← Что показать работодателю (артефакт дня, формулировки для резюме, 1–2 стр)
└── glossary.md      ← ≥ 6 терминов, формат «**Термин (English)** — объяснение»
```

Объём книги — **15–30 страниц**. Больше — значит, книга не будет прочитана за день. Режь.

Нумерация книг **01–07** (не 00): ридер парсит `b` через `parseInt`.

## Требования к содержанию

- **Язык:** русский, на «ты», термины с английским оригиналом при первом упоминании: «реранкинг (reranking)».
- **Никакой воды.** Без «в наше время ИИ развивается стремительно». Каждый абзац — либо факт, либо решение, либо пример.
- **Факты сверять**, не брать из памяти модели: версии библиотек, имена моделей, эндпоинты провайдеров
  (YandexGPT, GigaChat, OpenRouter), API RAGAS/Langfuse/LangGraph. Использовать context7 или веб на момент написания.
  Если сверить нельзя — писать «на момент написания (сентябрь 2026)» и давать команду, которой читатель проверит сам.
- **Код только в блоках с языком** (```python, ```bash, ```yaml, ```sql, ```json). Код рабочий, без `...` в середине.
- **Лаба — в своих проектах.** Пути реальные: `~/proj/web-agent/...`, `~/proj/ai-agent-memory/...`.
  Самостоятельные скрипты лаб — в публичном репозитории портфолио `~/proj/ai-labs/dayN-…/`; правки web-agent и ai-agent-memory — в их собственных репозиториях. Так каждый артефакт виден работодателю.
- **Не дублировать** книгу 23 devops (Ollama/Open-WebUI/nginx) и лекции Anthropic по MCP — ссылаться.
- **Диаграммы Mermaid** — минимум 2 на книгу, у каждого узла `style … fill:#…,color:#fff` из палитры
  (`#2d2d2d` вход, `#1a5276` шаг, `#1e8449` успех, `#6e2f1a` ошибка, `#7d6608` данные, `#4a235a` внешнее).
- **Честность про рынок:** где требования вакансий расходятся с реальной практикой — говорить прямо.

## Проверки и ограничения

Валидатор проверяет явные шаблоны-заглушки, синтаксис Python/Bash, структуру глав,
локальные ссылки и манифест. Обычное слово «написать», heredoc и многоязычные примеры
допустимы; не искажай учебный текст ради ложного срабатывания регулярного выражения.
Для flowchart используй палитру; sequenceDiagram/stateDiagram имеют другой синтаксис.

`labs/` синхронизируется из именованных блоков: первая строка
`# ~/proj/ai-labs/dayN-topic/file.py` (SQL: `--`), JSON: комментарий
`<!-- lab: dayN-topic/file.jsonl -->` непосредственно перед блоком (тот же маркер годится и для
обычного многострочного JSON вроде `.vscode/settings.json`, не только JSON Lines).
Изменяй источник в книге и запускай `scripts/sync_labs.py`, не правь генерируемую копию.
В лабораторных по умолчанию публичные fixture; приватные данные/индексы/ключи — вне Git.

**Скрипты лаб — без аргументов командной строки.** Читатель открывает файл в VS Code и жмёт ▶ Run;
`argparse`/`sys.argv` в исполняемых блоках `dayN-*` — ошибка ревью, не стиль. Вместо флагов —
именованные константы блоком `# --- НАСТРОЙКИ ---` сразу после импортов; чтобы получить другой
результат, читатель меняет константу и запускает файл снова. Если день пробегает несколько
конфигураций подряд (пример: день 2 индексирует три разных снимка), так и пиши в прозе: «поставь
`COLLECTION = "…"`, сохрани, нажми Run», а не команду с флагом. Если один скрипт закономерно имеет
несколько независимых сценариев работы (пример: `red_team.py` — DRY RUN / живой прогон / офлайн
пересчёт), это тоже булевы/строковые константы, а не флаги `argparse`.

Первая строка каждого исполняемого скрипта дня (после docstring, если есть) — `import labkit`.
Модуль `labs/labkit.py` (генерируется из книги 01, см. её главу 2) при импорте сам читает `.env`
(`export KEY=value`, без ручного `source`) и даёт общие пути: `labkit.DATA` (входные файлы читателя),
`labkit.OUT`/`labkit.out_dir("dayN")` (результаты), `labkit.FIXTURES`, `labkit.LOCAL`. Ключ/секрет —
`labkit.env("NAME", required=True)`, необязательная переменная — `labkit.env("NAME", "default")`.
Для импорта модуля другого дня — `labkit.use_day("day2-rag-eval")` перед `from common import ...`,
не ручной `sys.path.insert`. Полный список переменных недели документируется один раз в
`~/proj/ai-labs/.env.example` (генерируется из книги 01); новая переменная в любом дне — сразу
туда, закомментированной секцией с номером дня.

**Комментарии в коде — для читателя, который не знает библиотек.** Каждая нетривиальная строка
(декоратор, вызов метода незнакомой библиотеки, «магическое» число) — короткий `#`-комментарий
на русском, что это делает и зачем. Ориентир по плотности — существующий код дней 1–7 после
правки 2026-09-07: `git log` этого коммита в `docs/books/`. Не комментируй очевидное (`x = x + 1  # прибавить 1`).

**Часть исполняемых файлов экспортируется как `.ipynb`, не `.py`.** Список — `NOTEBOOK_ENTRYPOINTS`
в `scripts/sync_labs.py`; конвертация — `scripts/py_to_ipynb.py` (percent-style деление на ячейки
по границам `def`/`class` и пустых строк между верхнеуровневыми блоками, только стандартная
библиотека). Книга не меняется: маркер первой строки остаётся `# ~/proj/ai-labs/…/file.py`, язык
блока — `python`, `ast.parse` и остальные проверки идут по этому тексту как обычно; `sync_labs.py`
сам решает, писать `.py` или `.ipynb` на диск. В `NOTEBOOK_ENTRYPOINTS` годится файл, который
читатель запускает целиком и смотрит вывод, и который **не импортирует ни один другой файл этого
дня** (`from <module> import ...`) — если импортирует, оставь `.py`, ноутбук нельзя импортировать
как модуль без отдельных инструментов. Перед добавлением файла в список проверь код на `Path(__file__)`
и `__file__` вообще: в ячейке Jupyter это имя не определено (`NameError`), нужен путь через
`labkit.ROOT / "dayN-slug"` вместо `Path(__file__).resolve().parent`. Проверка синтаксиса ноутбуков —
часть `scripts/check_project.py` (склеивает код-ячейки и делает `ast.parse`); для реальной проверки
исполнения (не только синтаксиса) — `pip install nbclient nbformat` во временное окружение и
`nbclient.NotebookClient(...).execute()`, эти два пакета не входят в `labs/requirements.txt`
(они не нужны читателю, только автору при проверке).

## Порядок работы

1. Прочитать этот файл, `AUTHORING-CONVENTIONS.md`, `README.md` (карта недели) и ТЗ книги `AGENT-INSTRUCTIONS-book-0N.md`, если есть.
2. `book.md` → `chapter-01.md` → `chapter-02.md` → `chapter-03.md` → `chapter-04.md` → `glossary.md`.
   После каждой главы: `python3 validate-book.py 0N-slug chapter-0K.md`.
3. Полная проверка `python3 validate-book.py 0N-slug` → `PASS`.
4. Зарегистрировать книгу в `files.json` (массив `{file,title}` в `courses["0N-slug"]`, глоссарий — последним).
5. Добавить `COURSE_META["0N-slug"]` в `index.html`, `COURSE_NAMES["0N-slug"]` в `reader.html`, бампнуть `ASSET_VERSION` в обоих.
6. Один коммит на книгу: `Book 0N (Title): initial`. Правки — `Book 0N (Title) chK: <что сделано>`.
7. Для согласованной публикации: offline gate, браузер и build-only, затем `./deploy-pxhome.sh`; отдельно проверить публичный HTTPS. Без запроса на публикацию оставить изменения локально.
