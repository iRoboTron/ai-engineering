# Правила написания книжной серии (переиспользуемые)

Это дистиллят «наработок» из курса DevOps — общие правила и технические
конвенции, которые переносятся в любую новую серию книг (web-testing и др.).
Файл копируется в новый проект скриптом `scaffold-book-series.sh`.
Здесь **нет** контента конкретного курса — только как писать и как устроен движок.

---

## 1. Структура проекта-серии

```
<project>/docs/books/
├── index.html          ← каталог (движок, из devops-шаблона)
├── reader.html         ← читалка (движок, из devops-шаблона)
├── files.json          ← манифест: { "courses": { "<книга>": [ {file,title}, ... ] } }
├── NN-book-slug/       ← папка книги (NN — двузначный номер)
│   ├── book.md         ← оглавление книги (заголовок + ссылки на главы)
│   ├── chapter-00.md   ← главы
│   ├── chapter-01.md
│   ├── appendix-a.md   ← приложения (если есть)
│   └── glossary.md     ← глоссарий книги (обязателен)
└── AGENT-INSTRUCTIONS-*.md  ← ТЗ для ИИ-агента на книгу (НЕ деплоится)
```

Имя файла = параметр читалки: `reader.html?b=NN&c=<файл-без-.md>`
(`c=book` → book.md, `c=1` → chapter-01.md, `c=a` → appendix-a.md).
`b` — номер из имени папки (`22` для `22-password-storage`).

---

## 2. Принципы написания

- **Одна команда/идея — одно объяснение.** Сначала зачем, потом как.
- **Контекст важнее синтаксиса.** Читатель должен понимать, зачем шаг.
- **Никакой воды.** Без «в наше время всё быстро меняется».
- **Реальные примеры** из практики, а не абстрактные `foo/bar`.
- **Упражнения после каждой главы** + **чеклист главы** в конце.
- **Find-and-fix драллы** (`debug-drill.md`): дать сломанный конфиг/команду и
  попросить найти и починить — сильнее закрепляет, чем чтение.
- **Один коммит на книгу.** Правки логируются; сообщение вида
  `Book NN (Title) chM: <что сделано>`.

---

## 3. Диаграммы (Mermaid)

Вставляй схему там, где текст описывает поток, состояния или последовательность.
Типы: `flowchart LR/TD`, `sequenceDiagram`, `stateDiagram-v2`, `block-beta`.

**Единая палитра курса** (одинаковая во всех книгах):

| Роль узла            | Цвет fill  |
|----------------------|------------|
| Старт / вход         | `#2d2d2d`  |
| Процесс / шаг        | `#1a5276`  |
| Успех / результат    | `#1e8449`  |
| Ошибка / опасность   | `#6e2f1a`  |
| Внимание / хранение  | `#7d6608`  |
| Особое / внешнее     | `#4a235a`  |

Всегда `color:#fff` к заливке. Перенос строки в подписи — `\n` внутри кавычек:
`A["Мастер-пароль\nна устройстве"]`.

```mermaid
flowchart LR
    A["Вход"] --> B["Шаг"] --> C["Готово"]
    style A fill:#2d2d2d,color:#fff
    style B fill:#1a5276,color:#fff
    style C fill:#1e8449,color:#fff
```

Проверяй баланс огораживающих ``` и скобок/кавычек в mermaid перед коммитом.

## 4. Глоссарий (обязателен в каждой книге)

Отдельный `glossary.md` в папке книги. Формат: термины по алфавиту,
на русском с англ. оригиналом в скобках, короткое определение «на пальцах» +
где встречается в книге. Добавляй запись в `files.json` этой книги
(обычно последним пунктом, `title: "Глоссарий"`).

---

## 5. Деплой

- Локально всё в `docs/books/` (плоско). На сервере раскладка: `index.html`/
  `reader.html`/`files.json` в корне docroot, папки книг — в подкаталоге `books/`.
  Читалка сначала грузит `books/<книга>/<файл>`, потом запасной `<книга>/<файл>`.
- **nginx vhost**: `try_files $uri $uri/ =404;` — НЕ `/index.html`,
  иначе отсутствующие `.md` вернут 200 и сломают запасной путь читалки.
- При изменении контента бампай `ASSET_VERSION` в `index.html` и `reader.html`
  (сброс кэша). Деплой-скрипт — `deploy-pxhome.sh` (шаблон копируется скаффолдером;
  задай в нём свой `SITE_DIR`).
- Публикация на pxhome: отдельно проверить DNS, NPM proxy host и TLS для конкретного
  домена. Wildcard DNS не гарантирует наличие proxy host или сертификата.

---

## 6. Кастомизация движка под новую серию

После скаффолдинга открой `index.html` и поправь под серию:
`COURSE_NAMES`, `COURSE_ALIASES`, `COURSE_PARTS` (разбивка на части/диапазоны
номеров), заголовок `<title>`, блок «Об авторе». `files.json` стартует пустым
(`{"courses":{}}`) — наполняется по мере добавления книг.

## 7. Проверяемость лабораторных

- Markdown — источник именованных примеров; первая строка `# ~/proj/ai-labs/dayN-…/file.py`
  задаёт путь экспорта. Для JSON перед блоком используется `<!-- lab: dayN-…/file.jsonl -->`.
- `python3 scripts/sync_labs.py` обновляет код; `--check` обнаруживает рассинхронизацию.
- Примеры исполняемые, без пропусков. Частичный production-патч явно обозначается как
  фрагмент и не считается готовой интеграцией.
- Контроль оформления не равен проверке исполнения: offline gate, браузер, локальная
  интеграция и вызовы провайдеров — отдельные уровни доказательств.
- По умолчанию только безопасные fixture, localhost-bind, прикладные роли без
  superuser/BYPASSRLS, запрет экспорта ключей и частных входов.
- Dependency lockfile фиксирует транзитивные версии. Переход на latest требует повторной
  проверки, а старый pin не является гарантией безопасности для production.
- Minimum/stretch и уровни концепт/лаба/прод должны совпадать в book, лабе и резюме.
- Тайминг считается оценкой до реального хронометража; личные факты и цифры не сочиняются.
